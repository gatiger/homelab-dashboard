# Homelab Dashboard v0.20.0

v0.20 adds a generic, reboot-aware host-update workflow and enables **TrueNAS System → Update & reboot** as its first implementation.

## Highlights

- Host/service update scope is now part of provider capability metadata.
- Supported host updates require a separate explicit confirmation and dedicated `updates:host` permission.
- TrueNAS System can detect and install a reported operating-system update through the native TrueNAS JSON-RPC update job API.
- TrueNAS System is permanently excluded from **Update All**; host updates must be started individually.
- Host-update job state is persisted before the disruptive operation and survives a Dashboard restart.
- After a host reboot, Dashboard reconnects and verifies that the managed system is ready on the expected version.
- If Dashboard itself is hosted on the TrueNAS system being updated, startup recovery resumes verification when the Dashboard container returns. It does not send the update command a second time.
- Owner and Admin roles can start supported host updates. Editor and Viewer roles remain read-only for update actions.
- GitHub Actions definitions use Node.js 24-compatible action releases to remove the Node.js 20 deprecation warnings seen in v0.19 CI.

## TrueNAS permissions

Monitoring-only credentials may not be sufficient to install an operating-system update. The TrueNAS API key used by the reusable Connection must be authorized for the native system-update operation (including TrueNAS `SYSTEM_UPDATE_WRITE`) and the system/update read operations used for status and post-reboot verification.

Use the least-privileged TrueNAS account/API key that provides the operations you intend to expose.

## Host-update safety

A host update can interrupt every service running on that host. Homelab Dashboard therefore:

- requires explicit confirmation;
- never places a host update in Update All;
- persists the job before starting it;
- expects and represents a temporary disconnect as **Reconnecting**;
- verifies the expected version after the host returns; and
- never blindly retries the disruptive update after Dashboard itself restarts.

If Dashboard runs on the same machine and that machine fails to boot, Dashboard cannot report the failure because it is unavailable too. Running Dashboard on an independent management host remains the most resilient deployment, but it is not required.

## Upgrade

No Compose, environment-variable, or manual database changes are required. Preserve `/app/data` as usual. See `docs/UPGRADE-v0.20.md`.
